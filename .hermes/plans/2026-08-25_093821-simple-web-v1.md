# Simple Web V1 Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. The configured coding worker is `openai-codex/gpt-5.6-luna`; the main agent must review each task for specification compliance and code quality before continuing.

**Status:** APPROVED by Vadim on 2026-08-25, including the component-engine, engine-only Vitest, and separate CLI-app amendments below.

**Goal:** Build a small, deterministic, browser-first sandbox of AI Startup Lab Tycoon that proves the core `research → design → train → evaluate or gamble → launch → operate → build successor` loop without authored story, advisors, Chronicles, meta-progression, or late-game systems.

**Architecture:** Extend the existing pnpm/Turborepo repository rather than re-scaffolding it. Put all game rules in a pure, component-based TypeScript `packages/engine` package; compose explicit systems over serializable state components rather than building one monolithic reducer. Render one responsive TanStack Start application in `apps/web`; persist one autosaved run per Better Auth user through the existing Hono → oRPC → Drizzle → D1 path. Better Auth's anonymous plugin creates the V1 user/session automatically; account conversion is deferred. Put the development/balance CLI in its own workspace app at `apps/sim-cli`.

**Tech Stack:** TypeScript 6, pnpm workspaces, Turborepo, Vitest for `packages/engine` only, React 19, TanStack Start/Router/Query, Tailwind CSS 4, existing shared shadcn components, Better Auth anonymous plugin, Hono, oRPC, Drizzle, Cloudflare D1, and a Node-compatible TypeScript CLI under `apps/sim-cli`.

**Canonical direction:** `docs/ULTIMATE_VISION.md` remains the long-term product north star. This plan defines a deliberately smaller V1 and overrides that document only for V1 scope, not for eventual direction.

## 1. V1 Scope Contract

### 1.1 Player-facing promise

In a 30–60 minute intended play session, the player can reach the first multimodal milestone and may continue the sandbox afterward. The player:

1. Starts with one team, limited cash, and limited compute.
2. Researches a compact tree.
3. Names and designs a flawed text model.
4. Trains it while choosing how much compute to commit.
5. Evaluates uncertain scores or launches early.
6. Operates a Chat or Developer API product.
7. Experiences serving-versus-training compute pressure and mechanical incidents.
8. Builds an assistant successor using a continued, distilled, or fresh foundation.
9. Unlocks and launches a multimodal model.
10. Receives a clear milestone after the first multimodal launch, then continues operating and expanding until bankruptcy, trust collapse, or a manual restart.

### 1.2 Included systems

- Explicit **Advance Week** turn loop; no background simulation.
- One company setup: company name and deterministic seed only.
- One to three teams; one project per team.
- Five resources: **Cash**, **Compute**, **Insight**, **Trust**, **Hype**.
- Three research eras: **Text**, **Assistant**, **Multimodal**.
- Three research branches: **Models**, **Infrastructure**, **Products & Safety**.
- Approximately 12 research nodes total.
- Model naming and a compact designer:
  - foundation: continued, distilled, or fresh;
  - compute tier: lean, standard, aggressive;
  - data mix: general, code, multimodal, totaling 100;
  - emphasis: capability, reliability, safety, efficiency, totaling 6 points.
- Hidden true scores with visible estimates and uncertainty bands.
- Two evaluation projects: capability and safety/reliability.
- Three product channels: Chat, Developer API, and Enterprise.
- Two visible rivals at the start and a third introduced later; each uses a distinct focus/archetype and a simple deterministic progress clock.
- Lightweight Seed and Series A funding rounds influenced by Hype, Trust, model progress, and product traction.
- Six incident types: outage, latency degradation, quality/safety scandal, compute cost overrun, enterprise SLA breach, and data/privacy incident.
- Mechanical facts/reports and blocking decisions; no authored dialogue.
- One versioned D1 autosave per Better Auth user, command log, and deterministic replay test harness.
- Responsive web interface for desktop and narrow mobile widths.

### 1.3 Explicitly excluded

- Advisors, character dialogue, bespoke events, Chronicle prose.
- Founder archetypes, doctrines, traits, meta-unlocks, Notebook, Gallery.
- Boards, regulators, quarterly Strategic Questions, rival internal-company simulation, and funding rounds beyond Series A.
- Full data inventory, provenance, licensing, consent, staleness/cutoff.
- Full brand equity and detailed lineage visualization.
- Edge/local, video, agent, world-model, robotics, and AGI systems.
- Office visualization, animation-heavy research tree, audio, native wrapper.
- Permanent-account signup/upgrade UI, cloud-sync conflict handling, multiple save slots, multiplayer.
- PWA installation work until the browser game is proven fun.

### 1.4 Mechanical reports are not narrative

The engine must still explain outcomes using typed facts. V1 cards may read:

```text
TRAINING COMPLETE — Aurora-1
Capability estimate: 61 ± 18
Reliability estimate: 47 ± 22
Serving cost estimate: 70 ± 12

Available actions: Evaluate / Launch Chat / Launch API / Shelve
```

No advisor needs to have an opinion. Causality still needs to be visible.

### 1.5 Milestone and loss rules

**Milestone:** the first multimodal launch produces a prominent mechanical summary and marks the run as having reached the V1 frontier. It does not end the run. Products, incidents, rivals, funding pressure, and successor development continue in sandbox play.

**Loss:**

- Cash reaches zero after upkeep and no current-week revenue can cover it.
- Trust reaches zero after an incident resolution.

Loss cards must list the three largest contributing facts from the current run. This is mechanical attribution, not a Chronicle. The player may start a new sandbox after loss.

## 2. V1 Weekly Phase Contract

The engine executes phases in this fixed order:

```text
1. upkeep      salaries + base operating costs + purchased compute
2. projects    team progress and project completion
3. research    insight gain and node completion
4. training    run progress and score generation
5. products    users, revenue, serving demand, satisfaction
6. rivals      simple focused progress clocks and launch pressure
7. funding     Seed/Series A project resolution and runway effects
8. incidents   risk accumulation and deterministic incident rolls
9. terminal    loss and multimodal-milestone checks
10. decisions  blocking/non-blocking decision assembly
11. reporting  typed facts for the web interface
```

`advanceWeek` rejects unresolved blocking decisions. Every calculation uses integers. No `Date`, `Math.random`, API call, browser object, or database is allowed in `packages/engine`.

### 2.1 Component-based engine structure

“Component-based” means explicit composition, not a speculative generic ECS framework:

```text
packages/engine/src/
  components/   serializable state slices and their invariants
  systems/      pure weekly systems operating on declared components
  data/         research, model, rival, incident, and balance definitions
  commands/     player-command validation and application
  selectors/    visible projections; hidden scores never leak
  testing/      golden-run helpers and deterministic fixtures
```

Canonical components are `company`, `teams`, `projects`, `compute`, `research`, `models`, `products`, `rivals`, `funding`, `decisions`, `reports`, `rng`, and `terminal`. Each component owns its state type, initializer, invariants, and selectors where relevant. Systems receive the whole immutable `GameState` plus a narrow `SystemContext`, but declare the components they read/write in code comments and tests. They return a new state plus typed facts; they do not call each other implicitly.

The top-level engine only composes:

```ts
type GameSystem = (
  state: Readonly<GameState>,
  context: SystemContext,
) => SystemResult;

const weeklySystems: readonly GameSystem[] = [
  upkeepSystem,
  projectsSystem,
  researchSystem,
  trainingSystem,
  productsSystem,
  rivalsSystem,
  fundingSystem,
  incidentsSystem,
  terminalSystem,
  decisionsSystem,
  reportingSystem,
];
```

Future augmentation should normally require: add/extend one component, add one pure system or command, emit typed facts, register the system explicitly, and add engine tests. Do **not** introduce inheritance hierarchies, a service locator, dynamic plugin loading, an event bus, or a generic entity-query language for V1.

### 2.2 Testing boundary

Install Vitest and test **only `packages/engine`**. Engine tests cover component invariants, commands, systems, deterministic RNG isolation, golden runs, milestones/losses, and replay. Web, auth, API, and D1 work are validated by typecheck/build plus focused manual/browser/API verification; do not create a second UI or backend unit-test stack in V1.

The separate `apps/sim-cli` imports the public engine API. During engine development, run 10 seeded games as a smoke distribution after meaningful rule changes. Before a balance checkpoint, run 50 seeded games and inspect milestone reach, loss causes, week distributions, rival timing, funding reach, compute shortages, and foundation choices.

## 5. Commit and Review Policy

For each implementation task:

1. Dispatch one fresh coding subagent with the exact task and relevant file context.
2. For engine tasks, require strict RED → verify failure → GREEN → verify pass → refactor with Vitest. For web/auth/API/CLI tasks, use typecheck/build plus the explicit manual/API/CLI verification in the task; do not add non-engine Vitest suites.
3. Main agent inspects the actual diff and test output.
4. Run a specification-compliance review.
5. Run a code-quality review only after specification compliance passes.
6. Fix findings before moving to the next task.
7. Commit only files belonging to that task.

Do not combine Tasks 1–8 into a giant "engine implementation" delegation. The deterministic boundaries are easier to review when each behavior arrives with its own failing test.

### 5.1 Pipelined concurrency scheme (updated 2026-08-25)

Reviews and development run concurrently via a **one-task pipeline offset** — reviews target a specific commit SHA while the coder proceeds to the next task, never the same files:

```text
Coder worker:   [Task N dev]────────[Task N+1 dev]────────[Task N+2 dev]
Reviewers:              [ox-alpha + Luna review N]────[dual review N+1]──
Insight (sol:batch):         (consulted async for hard problems, non-blocking)
Main agent:                     [final gate / reconcile N]───────
```

Rules that make this safe:

1. **Review against pinned SHAs.** A reviewer receives `commit <sha>` in its brief; later commits cannot invalidate an in-flight review.
2. **Fix-forward.** If reviews find issues after the coder has moved on, fixes are a small patch commit on top — do not idle the coder to wait for reviews.
3. **One writer per directory.** Never dispatch two coders whose tasks touch overlapping paths concurrently.
4. **Phase-aware fan-out:**
   - *Engine core (Tasks 4–7):* one coder, pipelined dual reviews (tasks are dependency-chained in `packages/engine`).
   - *Fan-out point (after Task 7):* up to 3 concurrent workers on disjoint trees — Task 8 (`apps/server`, `packages/api`, `packages/db`), Tasks 9–10 (`apps/web/src/game` shell), Task 16 (`apps/sim-cli`). Art generation (main agent) runs anytime.
   - *UI panels (Tasks 11–14):* max 2 concurrent coders on different panel files.
5. **Concurrency cap:** 2–4 workers in practice; provider quota and main-agent reconciliation are the real ceilings.
6. A blocked/failed review blocks only its own task, not the pipeline.

### 5.2 Provider assignment and fallback chain (approved 2026-08-25)

| Role | Primary | Fallback | Notes |
|---|---|---|---|
| Main agent (me) | `nous/stealth/ox-alpha` | — | orchestration, final gates, art generation |
| Coding worker | OpenAI Codex quota `gpt-5.6-luna` | OpenRouter exact `openai/gpt-5.6-luna` | same model, two quotas |
| Reviewer A | `nous/stealth/ox-alpha` | — | always runs |
| Reviewer B | OpenAI Codex quota `gpt-5.6-luna` | OpenRouter exact `openai/gpt-5.6-luna` | always runs, parallel with A |
| Insight agent | OpenRouter exact `openai/gpt-5.6-sol:batch`, max thinking | interactive sol if batch unavailable | see 5.3 |

Fallback rules:

1. On HTTP 429/524 from the primary quota, re-dispatch once on the fallback for the SAME task brief.
2. If both quotas fail, pause and report to Vadim instead of spinning or silently switching models.
3. Never mix providers within one task's coder→fix cycle without noting it in the commit/report provenance.
4. `OPENROUTER_API_KEY` lives in `$HERMES_HOME/.env`; OpenRouter calls use exact model IDs (exacto mode), no provider routing.

### 5.3 Dual-review reconciliation and insight agent

Every task gets **two independent reviewers** running in parallel against the pinned SHA:

- **Reviewer A:** ox-alpha (main-model family)
- **Reviewer B:** Luna via Codex/OpenRouter

Reconciliation procedure:

1. Both verdicts PASS → main agent does the final diff/test gate itself if the task is routine; otherwise feeds both reports + diff to the **insight agent** (`gpt-5.6-sol:batch`, max thinking) to produce a unified findings document.
2. Any FAIL/disagreement → the insight agent receives both full reports plus the diff and returns a unified document: confirmed issues (with severity), disputed findings with reasoning, and recommended fixes. The main agent arbitrates only if the insight output is ambiguous.
3. Confirmed shortcomings go back to the coding subagent as a fix task; the fix is verified by the same dual-review path (may be single-pass for small patches at main agent discretion).

The **insight agent** is a standing read-only subagent used by the main agent for big questions and hard problems (architecture decisions, gnarly debugging, balance math, review tie-breaks). It receives a distilled question plus relevant context/files and returns a report or answer only — it never writes files or commits. Batch-mode latency (minutes) is accepted by design; consult it asynchronously while other work continues.

### 5.4 Retry policy on provider failures

1. Worker dies mid-task on 429/524: check for partial commits. Clean tree → re-dispatch fresh on the fallback provider with the identical brief. Dirty tree → inspect, revert partial work, then re-dispatch.
2. Apply exponential backoff between provider retries; never hammer a rate-limited endpoint.
3. If all assigned providers for a role are limited, stop and inform Vadim with current pipeline state instead of degrading model quality silently.
